# 앱 변형(조건) 설계: v0.1 초안

> 상태: 초안이며, 구현하면서 확정합니다. PROTOCOL.md §2를 구체화한 문서입니다.
> 원칙(연구계획서 p.16): **핵심 기능과 테스트 목표는 네 변형에서 동일하게 유지하고, 상태가 반영되는 범위와 페이지 간 데이터 흐름만 바꿉니다.**

## 1. 두 요인의 조작 정의

| 요인 | 낮음 | 높음 |
|---|---|---|
| 상태 의존성 (S) | 조작의 효과가 **조작한 항목 자체**에만 나타남. 다른 조작이 갱신하는 파생 값(개수, 배지, 진행률)이 없음 | 조작이 **파생 상태**를 함께 갱신함. 파생 상태는 개수, 배지, 진행률, 현재 필터 결과, 상태에 따른 편집 가능 여부 등이며, 다음 단계의 동작이 이전 조작 결과에 의존함 |
| 페이지 간 상호작용 (P) | 목표에 필요한 정보와 조작이 **한 페이지**에 있음. 다른 페이지는 존재하지만 데이터를 공유하지 않음(화면 수 통제용) | 데이터가 **여러 페이지를 거쳐** 흐름. 예: 등록 페이지에서 만들고 목록 페이지에서 확인, 상세 페이지에서 수정하고 목록과 대시보드에서 확인 |

| ID | 목표 | 관련 요구사항 | 탐지 기회를 주는 결함 |
|---|---|---|---|
| G1 | 과제 등록과 입력 검증 | REQ-TASK-001, REQ-TASK-006 | F6 |
| G2 | 과제 완료 처리 | REQ-STATUS-001 | F1, F5 |
| G3 | 상태별 필터 | REQ-FILTER-002 | F2 |
| G4 | 과제 수정 후 반영 확인 | REQ-TASK-004 | F3 |
| G5 | 과제 목록 정렬과 현황 | REQ-TASK-002, REQ-DASH-001 | F4, F7 |

파일럿에서 ICC가 크게 나오면 목표를 9개로 늘립니다. 후보는 REQ-TASK-005(삭제), REQ-SEARCH-001(검색), REQ-FILTER-003(복합 필터), REQ-STATUS-002(미완료 처리)입니다.

## 3. 변형별 구현 방식 (예: G2 과제 완료 처리)

| 변형 | 구현 |
|---|---|
| A (S↓ P↓) | 목록 페이지의 행에서 완료를 체크하면 **그 행의 표시만** 바뀜 |
| B (S↑ P↓) | 같은 페이지에서 완료를 체크하면 행, 상단 완료 배지 개수, 진행률, 현재 필터 결과가 **동시에** 갱신됨 |
| C (S↓ P↑) | **상세 페이지**에서 완료 처리한 뒤 목록 페이지로 돌아가면 그 행의 상태가 반영됨 (파생 값 없음) |
| D (S↑ P↑) | 상세 페이지에서 완료 처리하면 목록 행, **대시보드** 완료 개수, 과목 페이지 진행률이 모두 갱신됨 |

나머지 목표(G1, G3, G4, G5)도 같은 원칙으로 표를 채웁니다. **구현할 때 확정할 항목**은 다음과 같습니다.
- 변형마다 seed data가 동일한지 (사용자 1명, 과목 3개, 과제 12개 내외)
- 변형 간 페이지 수와 DOM 규모 차이 (`snapshot_stats`로 자동 기록, 차이가 크면 A·B에 페이지를 추가)
- 각 목표의 시나리오 파일(`research/scenarios/<goal>-<variant>.json`)에는 **사용자가 관찰할 수 있는 기대 동작만** 적습니다. 변형 ID나 결함 정보는 적지 않습니다.
