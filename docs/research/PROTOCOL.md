## 1. 연구 질문과 가설

**제목(가):** 웹 애플리케이션의 기능적 복잡도가 LLM 생성 E2E 테스트의 결함 탐지에 미치는 영향: 상태 의존성과 페이지 간 상호작용을 중심으로

| | 내용 |
|---|---|
| RQ1 | 상태 의존성(S)과 페이지 간 상호작용(P)은 결함 탐지율에 어떤 영향을 미치는가? |
| RQ2 | 두 요인의 주효과와 상호작용 효과는 어떻게 나타나는가? |
| RQ3 | 복잡도에 따라 미탐지·오라클 오류·실행 실패·수정 노력은 어떻게 달라지는가? |
| H1 | S가 높을수록 탐지율이 낮아진다. |
| H2 | P가 높을수록 탐지율이 낮아진다. |
| H3 | S와 P가 모두 높은 조건(D)에서 저하가 가장 크다. 두 효과를 단순히 더한 것보다 크다(S×P 상호작용). |
| H4 | 복잡도가 높을수록 실패 중 실행 실패보다 오라클 오류와 미탐지가 차지하는 비중이 커진다. |

결과는 **"고정된 모델 1종과 설정에서 나타나는 복잡도 효과"**로 해석한다. 모델 간 우열은 주장하지 않는다.

## 2. 실험 설계: 2×2 앱 변형

|  | 페이지 간 상호작용 낮음 (P↓) | 페이지 간 상호작용 높음 (P↑) |
|---|---|---|
| **상태 의존성 낮음 (S↓)** | A | C |
| **상태 의존성 높음 (S↑)** | B | D |

- **조건 = StudyFlow의 앱 변형(variant).** 같은 코드베이스에서 `STUDYFLOW_VARIANT`(백엔드)와 `VITE_STUDYFLOW_VARIANT`(프론트엔드)로 전환한다.
- **통제 항목**
  - 테스트 목표(goal) 집합을 네 변형에서 동일하게 둔다.
  - seed data, 브라우저, 뷰포트(1280×800), 로케일(ko-KR)을 동일하게 둔다.
  - LLM 1종, 모델 버전, 프롬프트를 고정한다.
- **화면 수 통제:** A·B에는 상호작용이 없는 페이지를 추가해, 화면 수 차이가 효과에 섞이지 않게 한다.
- **공변량:** 시작 페이지의 DOM 노드 수와 인터랙티브 요소 수를 하네스가 자동으로 기록한다(`snapshot_stats`).
- 변형별 구현 명세는 [`research/design/conditions.md`](../../research/design/conditions.md)에 둔다.

**설계상 장점:** 테스트 목표가 네 변형에서 같기 때문에, 같은 목표 안에서 변형만 바꿔 비교할 수 있다(within-goal 비교). 목표마다 다른 난이도는 무선효과로 흡수된다.

## 3. 표본 구조

| 단위 | 정의 | 기본안 | 확장안 (파일럿 ICC가 클 때) |
|---|---|---|---|
| 시나리오 | 목표 × 변형 | 5 × 4 = 20 | 9 × 4 = 36 |
| 스위트 | 시나리오 × 생성 반복(3) | 60 | 108 |
| 관측치 | 유효 스위트 × 그 변형에 적용 가능한 결함 | 약 240–350 | 432–648 |

- 분석 단위는 테스트 실행이 아니라 **(스위트 × 결함)**이다.
- S와 P는 시나리오 단위로 정해진다. 따라서 실질적인 검정력은 관측치 수보다 **목표 수와 변형 수**에 좌우된다.

| 샘플링 | 제공자 기본값을 쓰고 변경하지 않는다. 무작위성은 생성 반복(3회)과 스위트 무선효과로 다룬다. |
| 전환 기준 | 파일럿에서 A 조건 탐지율이 30% 미만이거나 유효 스위트 비율이 70% 미만이면, 바닥 효과로 보고 상위 모델 전환을 지도교수와 협의한다. |

**관찰된 위험 (2026-11-12)**
- `gemini-3.5-flash`를 요청했는데 서버는 `gemini-3.6-flash`로 응답했다. 모델 이름이 조용히 다른 버전으로 연결될 수 있다는 뜻이다.
- 하네스는 호출마다 `model_version`을 기록한다. 실행 도중 버전이 바뀌면 경고를 남긴다(`run.json`의 `model_versions_seen`).
- **본 실험 중에 버전이 바뀌면 그 실행분은 분리해서 보고한다.**

**재현성 보장 방식**
- 프롬프트 원문의 해시, 응답 원문, 생성된 모든 코드, 앱 git commit, 각종 도구 버전을 저장한다.
- **평가 단계(Stage 2)는 저장된 코드로 언제든 다시 실행할 수 있다.** 생성 단계(Stage 1)는 모델이 제공되는 동안에만 다시 할 수 있다. 논문에도 이 구분을 그대로 명시한다.
- 본 실험은 짧은 기간(1–2주)에 몰아서 실행한다. 일별 실행에는 A–D 조건을 섞어, 날짜 효과가 특정 조건에 몰리지 않게 한다.

## 5. 파이프라인

### Stage 1: 생성과 정상 앱 검증 (`harness/generate.py`, 구현 완료)
0. **사전 점검 (자동):** 앱에 결함이 켜져 있으면 실행을 거부한다. 시나리오의 변형과 실행 중인 앱의 변형(`/api/__research/info`)이 다를 때도 거부한다.
   - **DB 초기화:** snapshot 캡처 전과 Playwright 실행 전마다 DB를 seed 상태로 되돌린다(`POST /api/__research/reset`). 초기화는 스위트 실행 단위로 하며, 한 파일 안의 테스트들 사이에서는 하지 않는다. 따라서 같은 파일의 테스트끼리 상태를 공유한다. 이로 인해 생기는 실패는 LLM 테스트 설계 결과로 보고 그대로 판정한다.
1. 시작 페이지의 ARIA snapshot을 캡처한다. **LLM이 보는 앱 정보는 이것과 시나리오 명세뿐이다.**
2. LLM이 Playwright 테스트 파일을 생성한다(step 0).
3. 생성된 파일을 **정상 앱(결함 없음)**에서 실행하고 판정한다.
4. 실패하면 **정상 앱에서 난 실패 출력만** 돌려주고 수정시킨다. 최대 3회까지 한다(step 1–3).
   - 결함 정보, 결함 앱의 동작, 변형 ID는 어떤 프롬프트에도 들어가지 않는다(Obj2, 누출 방지).
   - 연구계획서 Fig 8의 피드백 루프를 이 형태로 제한한 것이다.
5. 유효해지면 3회 다시 실행해 불안정(flaky) 여부를 판정한다.
6. 최종 파일을 **고정(freeze)**한다. 이후 단계에서는 수정하지 않는다.
- 본 실험에는 사람이 개입하지 않는다. 연구계획서의 "Tool to ask Human"은 쓰지 않는다. 사람은 라벨 검증에만 참여한다.

### Stage 2: 결함 앱 평가 (`harness/evaluate.py`, 앱 기능 구현 뒤 작성)
고정된 유효 스위트 각각에 대해, 그 변형에 적용 가능한 결함마다 다음을 반복한다.
1. `STUDYFLOW_VARIANT`, `STUDYFLOW_FAULT=Fk`, `STUDYFLOW_REACH_LOG`를 설정하고 앱을 시작한다.
2. 스위트를 실행하고, 결함 도달 기록(reach marker)을 수집한다.
3. 아래 §6 규칙으로 판정한다.

## 6. 판정 라벨과 규칙

### 6.1 생성 단계 라벨 (정상 앱 기준, 자동 판정)

| 라벨 | 규칙 |
|---|---|
| `valid` | 모든 테스트가 통과 |
| `execution_failure` | 코드 블록 없음, 문법·변환 오류, 테스트 0개, locator를 찾지 못함, timeout |
| `oracle_error` | 요소는 찾았지만 기대값이 정상 앱과 다름 (Expected/Received 불일치) |
| `environment_error` | 앱 서버, 네트워크, 브라우저 문제, 또는 LLM API 호출이 최종 실패 |
| `flaky` | 유효 판정 뒤 정상 앱에서 다시 실행했을 때 한 번이라도 실패 |

### 6.2 평가 단계 라벨 (결함 앱 기준)

| 조건 | 라벨 |
|---|---|
| 정상 앱에서 통과 + 결함 앱에서 실패 + 결함 코드 도달 기록 있음 | `detected` |
| 결함 앱에서 통과 + 결함 코드 도달 기록 있음 | `missed` (결함 코드는 실행됐지만 검증하지 못함) |
| 결함 앱에서 통과 + 도달 기록 없음 | `no_opportunity` (테스트가 결함 경로를 지나가지 않음) |
| 결함 앱에서 실패 + 도달 기록 없음 | 다시 실행한다. 계속 실패하면 수동 검토로 보낸다. |

- **판정 단위는 스위트(파일)다.** 같은 파일의 테스트들은 DB 상태를 공유한다. 그래서 결함 때문에 한 테스트가 중간에 멈추면, 그 테스트가 정리하지 못한 상태 때문에 다음 테스트도 실패할 수 있다(연쇄 실패).
  - 이 현상은 `pilot-g2-B-001`의 Stage 2 미리보기에서 관찰됐다.
  - 테스트 단위로 분석할 때는 파일 안에서 **첫 번째로 실패한 테스트만** 결함 탓으로 본다. 그 뒤의 실패는 `cascade`로 따로 표시한다.

### 6.3 주분석에서의 처리 (사전 확정)
- **결과변수 `detected`:**
  - 1: `detected`
  - 0: `missed`, `no_opportunity`, 그리고 생성 단계에서 끝내 유효하지 않았던 스위트(`oracle_error`, `execution_failure`)
- **`environment_error`:** 다시 실행해서 해결되면 그 결과를 쓰고, 끝내 해결되지 않으면 분석에서 제외한다. 제외한 건수는 보고한다.
- **`flaky`:** 주분석에서는 0으로 둔다. 민감도 분석에서는 제외한다.
- **휴리스틱 판정의 검증:** `needs_review=true`로 표시된 판정과, 무작위로 뽑은 20% 표본을 평가자 2인이 독립적으로 다시 판정한다. Cohen's κ를 보고하며 목표는 0.8 이상이다.

## 7. 결함 카탈로그와 유효 결함 조건

- 결함 정의와 변형별 적용 가능성은 [`research/faults/catalog.yaml`](../../research/faults/catalog.yaml)에 둔다.
- **유효 결함 조건** (연구계획서 Tab 10)
  - 정상 앱에서는 발생하지 않는다.
  - UI나 API로 관찰할 수 있다.
  - 테스트 목표가 그 결함을 탐지할 기회를 가진다.
  - 환경 오류와 구분된다.
  - 한 번에 변이 하나만 적용한다.
- **동등 변이체 제거 (Obj4):** 결함마다 사람이 작성한 **기준 테스트(reference test)**를 하나씩 둔다(`tests/reference/F<n>.spec.ts`). 기준 테스트는 해당 변형의 정상 앱에서 통과하고, 결함 앱에서는 실패하면서 도달 기록을 남겨야 한다. 기준 테스트가 그 결함을 잡지 못하거나 도달 기록이 남지 않으면, 그 결함은 본 실험에서 제외한다.
  - 사람 작성 테스트의 역할은 이것으로 한정한다. LLM 테스트와의 성능 비교 대상이 아니다.
- **결함 유형과 조건이 섞이는 문제 (중요):** 요인 특이 결함(F1, F3, F4)은 일부 변형에만 존재한다. 이 결함들까지 넣고 조건 효과를 추정하면, 조건 효과와 결함 유형 효과를 구분할 수 없다. 그래서 다음처럼 나눈다.
  - **주분석(H1–H3):** 네 변형 모두에 적용되는 **공통 결함(F2, F5, F6, F7)**만 쓴다.
  - **보조 분석(RQ3):** 요인 특이 결함(F1, F3, F4)을 포함한다.

## 8. 분석 계획

**주모형** (혼합효과 로지스틱 회귀, R `lme4::glmer` 또는 Python `statsmodels`/`pymer4`):

```
detected ~ S * P + (1 | goal) + (1 | suite) + (1 | fault_type)
```

- **보고:** 고정효과의 승산비(OR)와 95% 신뢰구간을 중심으로 보고한다. p-value에만 의존하지 않는다.
- **민감도 분석**
  1. 공변량(DOM 노드 수, 인터랙티브 요소 수)을 추가한 모형
  2. flaky 스위트를 제외한 모형
  3. 요인 특이 결함까지 포함한 모형
- **RQ3:** 실패 유형(`missed`, `no_opportunity`, `oracle_error`, `execution_failure`)별 분포를 조건 간에 비교한다. 유형별로 이진 혼합효과 모형을 적합한다.
  - 수정 노력은 수정 횟수(`n_repairs`)와 토큰 사용량으로 측정한다.
  - **오라클 약화 지표:** 수정 전후 `expect` 개수 변화를 기록한다. 수정하면서 assertion을 지워 통과시켰는지 확인하기 위한 것이다.
- **조작 점검:** 변형별 화면 전이 그래프와 상태 의존 그래프의 지표(노드 수, 엣지 수, 경로 길이)로, 실제 복잡도가 설계 의도대로 달라졌는지 확인한다.
- **비용 지표:** 탐지한 결함 1개당 토큰 수 = 총 토큰 ÷ detected 수.

## 9. 파일럿 성공 기준 (연구계획서 Fig 11)
- 네 변형이 동일한 seed data로 실행된다.
- 조건마다 결함 3–4개 이상이 UI에서 관찰되고, 기준 테스트로 탐지된다.
- 로그, 스크린샷, 실패 시 녹화(trace, video)가 저장된다.
- 모든 실행을 라벨로 판정할 수 있고, 평가자 간 일치도 κ가 0.8 이상이다.
- 추가 기준: 모델 버전이 고정 상태로 유지된다. A 조건 탐지율 30% 이상, 유효 스위트 70% 이상이면 현재 모델을 유지한다.

## 10. 지도교수 승인이 필요한 결정
1. 모델: Gemini 무료 등급 `gemini-3.6-flash`를 주모델로 쓴다. 바닥 효과가 나타날 때만 유료 모델로 전환한다.
2. 목표 수: 기본 5개로 시작하고, 파일럿 ICC를 보고 9개로 확장할지 정한다.
3. 주분석 범위: 공통 결함(F2, F5, F6, F7)만 주분석에 쓰고, 요인 특이 결함은 보조 분석으로 돌린다.
4. 사람 작성 테스트의 역할: LLM 테스트와의 비교군이 아니라 결함 유효성을 검증하는 기준 테스트로 쓴다.
5. 제외 범위: GAE 결함 탐지 모델(Fig 5), RL 환경(Fig 6), RAG 오라클, 모델 간 비교는 후속 연구로 미룬다.
